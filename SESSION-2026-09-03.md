## 2. The bug worth remembering

Demoting a company's only Company Administrator to Vehicle Manager returned
`{"ok":true}`. The last-admin guard is
`losing_admin and _other_admins(...) == 0`. `_other_admins` had been re-keyed to
`ADMIN = ANY(r.grants)` and correctly returned 0 — but `_grants_user_management`
still computed `losing_admin` from `company:assign`, which Vehicle Manager
holds. False first operand, short circuit, no guard.

The demoted user was then refused permission to invite a replacement:
`You may assign: Vehicle Inspector, Vehicle Maintenance`. No self-service route
back; the company would have needed direct database access.

Two things this illustrates. First, re-keying one half of a two-part predicate
is worse than re-keying neither, because the remaining half looks correct in
isolation. Second, reading the code produced only a suspicion — running it
produced a reproduction. The suspicion had been carried in a `NOTE` comment for
most of the session and nearly shipped as a documented open item.

Generalisation worth a grep before deploy: any predicate treating
`company:assign` as a proxy for "administrator" is suspect under v2.0.

## 4. Process notes

Three edits during this session did not reach disk, each costing a round trip
and one producing a misleading green suite. Two habits followed from that and
are worth keeping:

- **After any edit, `grep` or `sed` the file before running tests.** A passing
  suite is not evidence an edit landed — nothing imported
  `BLOCKED_COMBINATIONS` at the time, so the suite was identically green with
  the constant absent.
- **Edit from the shell** (`python - <<'EOF'` with a match-count assertion)
  rather than the editor, when an edit must be verifiable.

Also: commands typed into the tab running `run_dev.py` go to the server's
stdin, not to bash. They echo in the log and do nothing.
